## Purpose and trust model

- **MCP connector credential:** Existing per-device or per-Zone URL, stored by the ChatGPT MCP client. Possession authenticates the connector, **not** an AI's authorization to work.
- **Agent Session Token:** Independently generated secret, returned **as model-visible MCP tool data** to the requesting AI. The requesting client explicitly passes it as `agentSessionToken` on every protected tool call. No OAuth provider, OAuth server, automatic refresh token, silent token rotation or client-hidden session-token storage is assumed.
- **Owner:** Signs into Relay Admin independently of ChatGPT; approves or rejects each pending Agent Session in a new **Agent Session Approvals** dashboard section. Approval never occurs from an MCP tool.
- **Global Remote Unlock and Remote Lock:** Any authenticated connector can use enabled tools while globally unlocked. Relay Admin supports 5/15/30/60-minute Remote Unlock and immediate **Remote Lock**, which ends the global unlock but **does not revoke individually approved Agent Sessions**. Up-to-48-hour/custom unlocks remain unimplemented.

These are two separate authorization methods: an approved scoped Agent Session OR the existing explicit global unlock. Session authorization does not set any global local unlock lease and does not grant root/sudo OS privilege.

## MCP workflow

1. Connect to the existing Zone/per-device MCP URL. Zone connectors expose `list_devices` and do not cross Zones.
2. Call `request_agent_session` with only the tools (`["*"]` for all enabled tools or explicit tool names), devices/scope and a purpose note. **The AI does not ask for a duration or set an inactivity timeout.** A Zone call requires `scope: "zone/all"` (includes future members) or `scope: "devices"` and current member device IDs. A direct device connector can request only that device. Old clients that still send `durationHours` or `idleHours` are accepted temporarily, but these legacy values are ignored.
3. MCP returns a one-time model-visible `agentSessionToken` and request ID in pending state. Pending secret is powerless. Pending approval requests expire after **15 minutes**; at most **eight per connector per hour**.
4. The owner visits `/admin` → **Agent Session Approvals**, verifies the requested connector, devices and tools, **enters the approval duration (1–720 hours, default 1h)** and clicks Approve once. For grants beyond 24h, the owner may choose 24h or 48h inactivity expiration (default 24h). The owner controls both time limits, not the AI. Reject and Revoke remain independent owner actions, not MCP tools.
5. ChatGPT calls `get_agent_session_status` using its token (status polling does not extend inactivity); once approved, passes `agentSessionToken` on protected MCP tools. The Worker checks session state, secret hash, original connector kind/id and connector-token hash, selected host/tool, sliding idle expiry and absolute expiry on **every call**. It strips the model-visible token before forwarding to the local Agent.
6. A successfully admitted protected tool call moves the idle deadline, but never past absolute approval expiry. Background status polling, reconnects and token-refresh traffic do not extend approval. Once expired or revoked, **a new owner approval** is required.

- A denied out-of-scope tool call **must not** revoke an otherwise valid session or renew its inactivity timer. A further permitted call with the same token and connector must still succeed unless the token has expired, been revoked, or was omitted by the MCP client. A later ChatGPT read failure without owner revocation remains an unresolved client-side acceptance question; the generic authorization error alone cannot identify the reason.

## Enforcement and persistence

- The existing Cloudflare `RelayAdmin` Durable Object stores session records and hashes, never plaintext tokens; no new Cloudflare DO class or migration is needed. Session request rate-limiting and authorization updates use Durable Object storage transactions. The UI shows one row per session, status, scope, creation time, last use and idle/hard expiry. Audit metadata excludes bearer values.
- An approved Zone session only authorizes currently valid membership in the original Zone. An explicit device set cannot expand to other members; `zone/all` intentionally includes future members. Rotating the connector secret also invalidates grants bound to the old connector secret.
- The Worker provides a trusted **per-request approved bit** to the Agent over the authenticated existing Worker↔Agent WebSocket. The Agent passes it to its separately authenticated local HTTP child using an additional ephemeral header secret that is never part of the MCP tool arguments. User-owned local loopback clients with the existing private local HTTP token keep their upstream OS-user authorization behavior.
- While remotely LOCKED and without an approved session, the Agent denies remote file reads, writes, shell and process/MCP operations; `workspace_info`, `list_workspaces`, MCP tool discovery and Zone `list_devices` remain available for connection setup. Globally unlocked devices follow upstream behavior.

## Explicit limitations / threat modeling

- **Token replay:** A leaked active model-visible bearer plus its originating connector URL can be replayed by another client until idle/hard expiry or revocation. The scheme cannot cryptographically identify a distinct AI model/conversation without sender-constrained credentials. A broad compromise of the MCP client provider may expose *both* credentials; there is no automatic protection in that scenario.
- **Prompt injection:** Hiding a connector URL from the model reduces direct extraction but does not prevent an authorized model from being deceived into executing unwanted commands within its approved scope. Owner approvals, scoped tools/hosts and revocation are enforced outside the model but cannot sanitize the content of permitted shell commands.
- **Global Remote Unlock:** The owner explicitly retained upstream exception: a stolen Zone URL is sufficient while its Agent is globally unlocked. This feature does not make that exception safe against a leaked connector.
- **Local Lock and Remote Lock are not Agent Session kill switches:** both end global unlock only. Approved Agent Sessions remain valid until revoked or expired. The owner explicitly declined an application-level Emergency Lockdown feature in favor of VM infrastructure controls if necessary. VM deletion does not itself erase Cloudflare connector credentials or grants; it stops execution on that deleted host.
- **In-flight work:** Revoking or expiring a grant prevents *new* approved requests. A command already admitted may still finish, and a persistent child process may keep running. Before production use, decide whether and how to cancel in-flight work and terminate owned processes upon revoke/expiry.
- **Local process boundary:** The Agent's per-request approval bit is trusted only over its authenticated Worker WebSocket; the second ephemeral key protects that handoff to the local child. Local same-OS-user processes with access to the independent local MCP HTTP bearer still retain upstream local access. This does not provide protection against a compromised host or another sufficiently privileged process under the same OS user.
- **Client usability:** ChatGPT may not reliably retain a model-visible token across conversations. Do not assume it will attach the token automatically like a separately configured OAuth credential. A missing/lost token cannot be retrieved from stored hashes; it requires a new request and approval.
- **Owner-secret isolation is NOT met on cc-sdev2 today:** the Relay Admin plaintext bearer and Worker setup secrets are currently backed up under `/data/copilot/workspace/.private/easy-local-mcp-staging/`, readable to processes running as Ubuntu `ubuntu`, the same OS identity as the managed Agent and temporary ChatGPT bridge. Once a model receives authorized shell access, it could read the Relay Admin credential and impersonate the owner, bypassing the intended independent approval trust boundary. Before production, the owner must move the live Relay Admin bearer into a password manager/device inaccessible to all managed Agent OS identities, rotate any previously accessible admin bearer if feasible, and isolate the temporary bridge. Current Worker stores only a hash; do not delete the only owner copy without a safe migration plan.
- **Coordinated staging and rollback:** Worker and Agent must be updated together. Staging was updated as a pair after local tests; original Worker version `596f3dfa-950f-4b04-bbfc-ad3393555200` and installed Agent commit `24caf11` remain rollback references. Production deployment requires a separate decision.
